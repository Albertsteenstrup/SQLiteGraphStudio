# Explore a database with Graph Studio

Answer the user's question using schema, relevant application code or documentation, and bounded row reads when the answer depends on data. Choose depth from the question and the evidence: a narrow answer may need one focused view; a broad model or process question may benefit from an overview followed by deeper tables, relationships, code paths, and real rows; a question about actual values should go directly to the relevant data. For a why or how question, trace enough of the mechanism, constraints, and representative evidence to explain the answer, rather than stopping at the first plausible table. Use as few or as many meaningful points as the answer needs. Stop when the question is answered, and deepen or redirect when the user asks. The agent chooses the subject, view actions, and sequence; Graph Studio renders the embedded evidence and step navigation; the coding agent explains through its own text or audio. The native app has no player or story reader.

## Connect and choose the source

Reuse the running Graph Studio app and this task's bound workspace. Do not start another app copy or repeatedly open the same source; use `studio_refresh_source` when the source changed. Close unneeded agent-owned tabs before opening more sources.

Use `studio_status` to check the local bridge. An explicit request to show something authorizes `studio_launch` if the app is closed. For an ordinary coding question where visualization would merely help, offer it. Call `studio_connect_context` once for this coding task. Keep its returned `context_id`, `client_task_id`, and secret `resume_token` in this task's own session state; never copy another task's capability or treat the task label as authentication. Include the exact `context_id` on every later app-bound call. If the MCP stdio connection reconnects while Graph Studio remains open, call `studio_connect_context` with the previous `context_id` as `resume_context_id`, plus the exact `client_task_id` and current `resume_token`. Save the rotated token from the response. A disconnected context is retained for up to 24 hours, with a cap of 128 detached contexts and 4,096 request receipts. The token is in-memory and does not survive Graph Studio restarting. Check `recovery_status`: if it says `ownership_released`, the user transferred the old tab; do not take it back implicitly. Resolve the source from an explicit file or connection, the current selected object, or an established task binding. If the user names a project folder, call `studio_scan_project` and inspect `available_engines`, `source_choice_required`, each candidate's `engine`, and `supports_rows`. If both PostgreSQL and SQLite are found and the user has not selected an engine or exact source, ask which model to use before opening one, even when one migration set looks more prominent. If several candidates remain within the selected engine, ask for the exact source when the answer could differ. A prior task binding or explicit source choice resolves this question; do not repeatedly ask. `studio_open_source` can open a migration-set folder or schema script at a chosen version, but that model has schema only, no rows to browse or queries to run. If the user wants actual values and the scan found only schema sources, explain that a database file or connection is needed rather than implying empty tables. When several workspaces are open, bind this task to the exact `workspace_id`; ask only if more than one plausible source remains. Check `studio_list_workspaces` and `studio_get_view` before changing an active explanation. For an explicit request to show a native live view, if `studio_get_view` reports `active=false`, call `studio_update_workspace` with `changes.activate=true` and `changes.activation_intent=foreground` before presenting it.

If MCP is unavailable, use the existing read-only database and repository tools to answer what you can. Preview and diff files have separate workflows in the sibling skills. Do not describe a native view as shown unless the app confirms it is visible.

## Live Graph Studio inside the conversation

For a visual explanation inside the chat, prefer `studio_show_workspace_inline`. It uses a dedicated native schema graph surface, like the embedded review, with explanation step controls in the card; `studio_show_data_inline` is a standalone row grid. Reuse this task's exact context/workspace/source. Check `studio_get_view` and, if the intended workspace is inactive, select it deliberately with `studio_update_workspace` (`changes.activate=true`); selecting it does not require activating the app window. The running app renders the embedded graph from its loaded model without needing a visible desktop window. An inactive/closed workspace must never fall back to whichever native workspace is visible.

Show one live inline view, then drive the explanation with the existing view and presentation tools. Prefer the graph at full width. Only add `open_table` to a point when actual records help explain it, or explicitly select a query pane with `set_layout` when query evidence is needed. Data appears beside the graph only for those points and closes on graph-only points, even if a desktop table remains open. The compact grid shows at most 10 rows and 20 columns from already loaded data; use the standalone row view for paging or detailed cell inspection.

The embedded card eases camera/focus changes, slides data panels in or out and fades captions. It preserves graph proportions through layout changes and confirms point visibility after its final frame and motion settle. Reduced motion applies steps immediately. Reader navigation and graph gestures interrupt ongoing motion; no animation introduces timed advancement. Wait for `point_visible` before explaining newly displayed evidence through Codex text or audio.

The embedded view uses Back/Next steps, with a step counter and no Play or End buttons. Its Graph Studio logo opens the same workspace in the native app, preserving the current step. Each step stays until the reader or MCP moves it. For an explanation through Codex text or audio, create manual points (`timing.advance=manual`) with `narration_mode=disabled`; explain the current rendered evidence in Codex, then call `studio_control_presentation` with `next` or `back` when the subject changes. Move the view before explaining the evidence it contains, and check rendered readiness before claiming it is shown. Avoid starting Graph Studio speech alongside Codex audio. Embedded step mode also suppresses local narration and timing for older authored points. Appending a point adds to the navigation without moving the reader's current step. The final step remains inspectable and Back stays available. Pan, zoom, selection and Fit work directly in the embedded graph and use a separate viewport. Restore step is available only after the view was changed or failed. Closing the card, expiry, or disconnect pauses the explanation and releases its lease. It never creates native controls or starts native speech. MCP End and Return remain available for explicit cleanup. Respect manual interaction. If another workspace is selected, the context expires or the source changes, the card labels and retains its last frame, then stops following. Reconnect the intended workspace explicitly. Never describe a retained frame as the current live state.

## Embedded row views

Prefer `studio_show_data_inline` when showing table values or a captured query result in the conversation. Include this task's exact `context_id` and either a `table_id` or a `result_id`. For tables, supply meaningful `column_ids` and any needed `filters`, single-column `sort`, or `search_text`. For queries, first start `studio_run_query`, wait for `studio_get_job` to report completed, then show its immutable `result_id`; paging never reruns SQL. The grid shows bounded pages, cell inspection, the table selection or executed SQL, and explicit query-cap/partial-cell labels. Hosts without MCP Apps receive a text preview and structured rows. A displayed page does not prove the complete result set.

This view uses the task's existing database workspace in the running app. Do not activate a workspace or open a native table/query pane merely to show embedded rows. Paging keeps the exact context, workspace and source; if they expire or change, resolve the intended source again rather than silently showing another source. Migration-only models have no row data. Use `studio_open_table` or `studio_show_query_results` when the user asks for data in the native app or when an embedded point needs rows beside the graph. Explain embedded values in the chat.

## Find evidence, then choose what to show

- Use `studio_search_schema`, `studio_describe_schema`, and `studio_find_relations` to identify exact table, field, and declared key IDs. A returned graph-edge `id` is for `studio_focus_keys`; use its separate `record_relation_id` for `studio_follow_record` or `studio_show_record_graph` after the user has inspected a full row with a stable identity. Read relevant code and docs for application behavior. Label code-derived relationships as application behavior or inference.
- For a broad data-model overview, inspect the catalog's scope and domain groups before choosing the sequence. Read `studio_get_annotations` for optional authored clusters and `overview_table_ids`, then verify any proposed anchor against the current schema and relevant code. These hints are useful defaults, not a prescribed route. Do not infer the whole model from the first connected neighborhood.
- Keep a readable path from a focused group to the whole model. Use `studio_show_tables` with `operation=all` and `highlight_table_ids` for an immediate context map, or a `show_context` point action with `table_ids` as an intermediate explanation step. The full catalog stays visible while those subjects and their internal relations are highlighted; other tables recede. Use `show_tables` for the next detail step. The reader can also use Show in full model / Return to detail in the same embedded card.
- Declared foreign keys may appear as graph edges. Tables related only by application logic can be displayed close together and explained in words; never add a visual relationship edge for them.
- Start with a small useful set of core and supporting tables when that helps. The user may ask for all connected tables; then cover the requested scope, possibly in several views, and disclose traversal limits. You may also show a subset, return to an earlier group, or expand farther when it makes the explanation clearer.
- For a request to understand the **whole** model, show the full catalog map at least once with readable domain-group titles and a few named anchors. Clear an incidental table selection or existing focus so it does not dominate that map. Explain the major domains and the model's main path in human language, with the actual table/view count and any schema-only limit. A full map is an orientation view; individual names may be too small to read there. Follow it with a readable bridge view of a few essential tables from different domains, then move into the user's area of interest. Keep one or two upstream/downstream anchors alongside a focused table when they clarify its place in the model, or return briefly to the map between deep dives. State when a readable subset is only a subset. For a narrow question, skip this tour and show the decisive evidence directly.
- Consider node size as one useful comparison on an overview. Read `studio_get_view.node_sizing_data` first: it reports full-catalog field range, available row-count coverage and range, and declared-relation coverage. Use `relations` when differing declared foreign-key counts help explain structural hubs; those counts do not measure business importance or application-only links. Use `fields` when width of the schema helps compare core records with supporting tables. Use `rows` only when available counts or estimates cover the tables being compared and differ enough to convey scale; qualify estimates, and do not use row sizing for schema-only migration models with no counts. Keep `uniform` when another metric adds little or the user has explicitly chosen it. These are choices for the question, not a required tour through all four metrics. The scale remains based on the full catalog even after a subset is shown.
- For an agent-led embedded point, put `{"type":"set_node_sizing","metric":"relations"}` (or the chosen metric) in that point's `actions` with the matching `show_tables` action, so the visual comparison is ready before the agent explains it. For an immediate view, call `studio_set_node_sizing` with `persist=false`. Explain once in ordinary language what larger nodes represent and what the comparison teaches about this model, rather than narrating the control change. Switch metrics only when a new question benefits from a different comparison; respect a user's manual choice and save a default only when requested. A presentation's Return control or `studio_restore_view` restores the metric captured with its view.
- Use `studio_show_tables`, `studio_select_objects`, `studio_expand_tables`, `studio_focus_keys`, `studio_arrange_tables`, and `studio_set_camera` as needed. When explaining one table, select that exact table and usually show it alone or with only the context needed for the claim. In a presentation point, set `target_table_id` so the table is selected even when several remain visible. Expand the target when a few relevant fields clarify the point; avoid expanding many wide tables at once. `studio_show_tables` fits the visible set and automatically compacts a sparse set of up to eight; use `studio_arrange_tables` when more control is useful. Verify that table names are readable at the resulting zoom and narrow the visible set or refit if they are not. Use `studio_set_camera` with `mode=fit_visible` after an exploratory pan or zoom when a fresh fit would help. Camera moves ease over 420 ms by default; choose `transition_ms` from 0 to 1200 when an instant cut or slower move better matches the explanation. Moving disconnected tables together changes layout only. Check `studio_get_view` to confirm the actual visible set after the user's graph filter, and use `graph_visible`, `visible_pane`, `rendered_table_ids`, and `visual_state` to check what is onscreen after motion settles. A rendered table ID means its card intersects the viewport, not that another card cannot overlap it. `visual_state` acknowledges graph drawing, not table or query content. Preserve a path back to the full view.
- When a live source has rows and a few actual values make the explanation clearer, prefer an embedded bounded page. For an embedded explanation point, use an `open_table` action to show only its relevant rows beside the graph. Prefer meaningful non-sensitive fields over a wall of IDs, and keep the exact table and column names visible.
- For row questions, use `studio_open_table`, `studio_configure_table`, `studio_fetch_rows`, `studio_inspect_value`, `studio_follow_record`, or a read-only query. `studio_inspect_value` defaults to a data-only database-side slice of one exact cell; use `value_offset` to page through long text or binary data, and check its type, byte/character counts, `complete`, `truncated`, and `has_more` fields. Binary slices are base64. Set `display_intent=show` only when the user wants the selected slice visible in Graph Studio; the inspector labels partial values and does not imply other fields or the record key were loaded. Return only relevant bounded values to the agent. Make the filter, sort, and SQL inspectable in the app. A displayed result is not necessarily a complete result set.
- Use `studio_annotate_view` for temporary human-language notes. When the user asks to keep an explanation, note, table description, or graph grouping across sessions, first call `studio_get_annotations`, then save with `studio_update_annotations` and its returned `metadata_revision` as `expected_metadata_revision`. On `METADATA_CONFLICT`, read again and merge the intended edits before retrying with a new `request_id`. Saved notes can describe an application-level association without creating a relationship edge.

Speak in ordinary language. Display exact identifiers and values when referring to them; pronounce code identifiers naturally. Keep schema facts, observed row values, code-confirmed behavior, and interpretation distinct. Tailor technical depth using `studio_get_preferences`. On first use, ask the user the questions returned by `studio_get_preferences` and save their answers through `studio_update_preferences`. Explicit feedback can also update preferences unless the user says it applies only this time.

Every agent-chosen visual emphasis or presentation point needs a reason tied to the user's question. Before showing it, identify what the user can learn from that view and the basis for the claim: inspected schema or keys, observed values, relevant application code or documentation, or a clearly labeled domain interpretation. Say the role, consequence, or distinction that makes the item worth seeing now. A caption such as “Here is the contract table” only names the object; it is not an explanation. For example, after verifying a foreign key, explain what it lets the user trace between the two tables. Do not infer actual row values from a schema, or present domain expectations as verified implementation. If the reason is not yet supported, inspect further or omit the point. A direct request to open a named table can be fulfilled as simple navigation without inventing a narrated claim.

Do not narrate staging such as selecting or expanding a card, or routine source bookkeeping such as a migration model having no row values. Use that information privately to choose the view. If unavailable rows prevent answering a question about actual values, explain the limitation once in chat and ask for a live source; do not imply the table is empty. Discuss the view controls or source availability in narration only when the user asks about them. Omit a point rather than fill it with a description of the UI.

## Live explanation and correction

Use an immediate view action for one useful display. Guided explanations belong exclusively in the embedded MCP view. Use `studio_start_presentation` with short, meaningful captions, typed view actions, `narration_mode=disabled`, and `timing.advance=manual`, then show or reuse `studio_show_workspace_inline`. The native app can inspect the same graph and source but has no explanation player or saved-story reader. Older narration/timing fields remain accepted as artifact metadata; they cannot enable local speech or automatic advancement.

Use the full-map orientation for a whole-model question; for other questions, start with an overview only when it helps, or show the decisive table, field, row, or query first. Add a new point when its subject or evidence meaningfully changes. Graph-only points fill the card; request an `open_table` action or a query pane only when data supports the claim. Each caption should explain what the visible tables, key focus, or grid establish. Move the view before explaining its evidence, and check `studio_get_presentation` or `studio_wait_events` for `point_visible=true` before claiming it is shown. Visibility requires an acknowledged, settled embedded frame; displaying the native app window does not acknowledge a point.

Append or revise points with `studio_update_presentation` as you learn more. Use `studio_control_presentation` with `back` or `next` when the user asks or the subject changes; the reader can use the same controls and current/total counter in the card. Respect manual graph inspection, which keeps the current point and may pause or invalidate its view. Restore it with `repeat` only when appropriate. If the user corrects a premise, replace obsolete pending points. MCP pause, end, and return remain available for cleanup; these are not native app controls. Saved `.sgexplanation` artifacts open only through `studio_open_explanation`; choose `start_mode=replay` for embedded steps, or `manual` to inspect the captured model and saved points through MCP. Historical rows come from the artifact and never query the original source.

Do not write to the actual database through MCP. The coding agent may implement requested changes using its normal development tools, then call `studio_refresh_source` and use the sibling `database-preview` or `database-diff` skill to show proposed or actual schema effects. Save descriptions, notes, groups, or explanation packages only when requested; ordinary highlights remain temporary.
